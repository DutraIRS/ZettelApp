## 1. Critical: alarm notifications run PowerShell built from note text (Windows)

`show_toast` (`winintegration.py:141`) puts the toast XML inside a PowerShell single-quoted string
and escapes only the ASCII apostrophe (`winintegration.py:160-161`, used at line 169). PowerShell
also ends single-quoted strings at ‘ ’ ‚ ‛ (U+2018 to U+201B; the PowerShell language specification
lists all five as single-quote characters). `toast_xml` escapes with `xml.sax.saxutils.escape`
(line 119), which leaves those characters alone. The XML carries the note's title and the first 140
characters of its text (`main_window.py:618-634`).

What the app builds for the title `Meeting’+(Start-Process calc)+’`:

```
$xml.LoadXml('<toast …><text>Meeting’+(Start-Process calc)+’</text>…');
```

PowerShell reads `'…Meeting’` as one string, runs `Start-Process calc`, and reads `’…'` as a
second string.

**Who can trigger it:** anyone who gets a note with an alarm into the vault. The archive and JSON
importer keeps the `alarm` field (`importer.py:297`), so a shared archive with an alarm in the past
fires right after import. A vault shared through OneDrive, which the docs suggest, works too. The
code runs as the user, with no prompt.

**It is also a plain bug:** an alarm whose title or first lines contain a typographic apostrophe
("Don’t forget", common in text pasted from Word or a phone) is a PowerShell syntax error, so the
toast never appears. `show_toast` returns True as soon as the process starts (line 194), so the tray
balloon fallback never runs either.

**Fix:** keep data out of the script. Pass the XML base64-encoded and decode it inside PowerShell
(`[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String('…'))`; base64 has no quote
characters), or hand it over through an environment variable or stdin. Add a test with U+2018 to
U+201B in the title and the text. Consider importing alarms as already fired. PowerShell was not run
here (this machine has none): confirm on Windows with a harmless command such as `Start-Process
notepad`.

## 2. Medium: the signing certificate and Snap Store credentials are visible to every step

`release.yml:59-62` puts `WINDOWS_SIGNING_CERT_BASE64` and its password in the job's `env`, so every
step of the job can read them: `pip install -r requirements-dev.txt`, the whole test suite,
`choco install innosetup` (a third-party Chocolatey package script, line 99) and the PyInstaller
build. One compromised package in any of these can copy the certificate. The same goes for
`SNAPCRAFT_STORE_CREDENTIALS` (line 184) in a job that runs `snapcore/action-build@v1` (line 192), a
third-party action pinned to a moveable tag. This is latent while releases are unsigned, and real
the day signing is switched on (it is on the roadmap).

**Fix:** move each secret into the `env:` of the one step that signs or uploads. Pin third-party
actions (`snapcore/action-build`, `gradle/actions/setup-gradle`, `actions/setup-java`) to commit
SHAs.

## 3. Medium: MCP setup is probably broken in the Snap and Flatpak builds

`mcp_command` (`settings_dialog.py:122`) handles the Store build, frozen builds and source checkouts.
The Snap and Flatpak builds fall through to the last case, so the MCP client's config gets
`sys.executable -m zettelapp.mcp_main` with a `PYTHONPATH` inside the sandbox. Claude Desktop runs on
the host, where `/app/…` (Flatpak) does not exist and the snap's Python is not meant to run outside
`snap run`.

The switch would not be seen either. Inside the sandbox, the app holds its lock under
`$XDG_RUNTIME_DIR/app/<id>/` (Flatpak, `paths.py:164-166`) or the snap's own runtime folder. A server
started on the host looks in `$XDG_RUNTIME_DIR/ZettelApp/`, finds no lock and refuses to start.
`snapcraft.yaml:32` already defines a `zettelapp-mcp` app that nothing points to, and
PLATFORM_CHECKS.md has no check for either build.

**Fix:** return `/snap/bin/zettelapp.zettelapp-mcp` under Snap and
`flatpak run --command=zettelapp-mcp io.github.dutrairs.zettelapp` under Flatpak, then add both to
PLATFORM_CHECKS.md. This was read from the code, not tested, because testing needs the packages
installed.

## 4. Low: Linux alarm notifications send note text as markup

`notifications.py:90-91` passes the title and the note text to `org.freedesktop.Notifications`
as-is. The notification spec lets the body carry a small markup set (`<b>`, `<i>`, `<a href>`,
`<img>`) when the server supports it, as GNOME Shell and KDE Plasma do. Note text such as
`<a href="https://…">` then becomes a link in the notification, and `<img src=…>` may make the
notification server load an image. That sits badly with "viewing a note never loads anything".
**Fix:** escape `&`, `<` and `>` in the body.

## 5. Low: `SHA256SUMS.txt` does not cover the `.flatpak` and `.snap` downloads

The v1.4.0 release ships six binaries, but `SHA256SUMS.txt` lists four: the `.exe`, the `.zip`, the
`.tar.gz` and the `.deb`. The `.flatpak` and `.snap` are missing, although the docs and website tell
people to install the downloaded `.flatpak` and README.md:84 says checksums are on the release page.
**Fix:** add both files to the checksum step in `release.yml`.

## Docs that say more than the code does

- **D1.** SECURITY.md:26 lists 1.3.x as the supported version; the current release is 1.4.0.
- **D2.** README.md:54: "imports are sandboxed". Imports are validated and size-limited, and run in a
  single transaction, but in the app's own process with its full rights. That is careful, but it is
  not a sandbox. The docs' own wording, "Safe imports", is accurate.
- **D3.** docs/privacy-and-security.md:87: "MCP clients can reach your notes only while ZettelApp is
  open and the MCP switch … is on." The switch is a consent gate for `zettelapp-mcp`, not a security
  boundary. Any program running as the user can read `zettel.db` directly, or create the
  `Local\ZettelApp.McpSwitchOn` event or hold the lock file to make the server believe the switch is
  on (`mcp_switch.py:25`, `mcp_switch.py:103-124`). That includes MCP clients with their own file
  tools, such as Claude Code. Say "ZettelApp's MCP server answers only while…".

## Code quality: SOLID, KISS, DRY, PEP 8

- **Q1. Single responsibility.** Three classes do most of the work:
  - `MainWindow`: 1,425 lines and 98 methods (`main_window.py:182`).
  - `OptionsDialog`: 1,158 lines and 46 methods (`settings_dialog.py:256`).
  - `Vault`: 1,184 lines and 89 methods (`storage.py:223`). It mixes schema migration, notes, tags,
    links, link types, search, alarms, review data, images, trash and backups. Splitting it by
    concern would make each part testable on its own.
- **Q2. Open/closed.** There are 72 platform checks (`sys.platform`, `IS_WINDOWS`, …) across 16
  files. `winintegration.py` also dispatches to `linuxintegration` (`registered_command`,
  `reveal_in_explorer`), so the "Windows integration" module is the Linux entry point too. macOS is on
  the roadmap. One platform interface, with an implementation per OS chosen once at start-up, would
  make macOS a new module instead of edits across 16 files.
- **Q3. DRY.**
  - The no-proxy loopback HTTP client is built twice (`anki.py:199`, `zotero.py:181`).
  - LIKE escaping is written out twice (`storage.py:560`, `storage.py:760`).
  - Two `_str` helpers behave in opposite ways: `importer.py:160` truncates, `mcp_server.py:129`
    raises.
- **Q4. KISS.** Some functions are very long:
  - `editor.py:89`: 188 statements.
  - `graph_page.py:101`: 154 statements.
  - `graph3d.py:138` (`paintEvent`): 110 statements, complexity 18.
  - `importer.py:387` (`_import_markdown_files`): 85 statements, complexity 28.
  - `mathrender.py:683` (`command`): complexity 30.

  In all, 25 functions exceed ruff's C901 limit of 10.
- **Q5. PEP 8 and lint coverage.** Ruff checks only E4, E7, E9, F, I and UP (`pyproject.toml:82`).
  - Measured against the project's own 100-column limit, 165 lines are too long.
  - Bugbear (B) and naming (N) rules are off. The N815 hits are Qt signal names, camelCase by Qt
    convention, which is fine. B would flag a `QModelIndex()` default argument (`note_list.py:67`),
    seven `zip()` calls without `strict=` and a `raise` without `from` (`embeddings.py:109`).
  - Turning on E501, B and C901 would keep these from growing.

## Checked and fine

- **Secrets:** Credential Manager and libsecret, with a memory-only fallback; keys never go into
  settings, are scrubbed from error messages, and are never sent to another origin on a redirect.
- **AI:** endpoints must be HTTPS (plain HTTP only for localhost); note text cannot break out of the
  prompt's wrapper elements.
- **Rendering:** Markdown is rendered without raw HTML, with allowlists for links and images; images
  load only from the vault's assets.
- **File links:** links to local files are only revealed in the file manager, never opened.
  Network paths and `file://host` are refused, and a missing file never reaches `os.startfile`.
- **Imports:** zip-slip and decompression-bomb checks, symlink checks in folder imports, Evernote
  files with entity declarations refused, YAML parsed with `safe_load`.
- **Database:** SQL uses bound parameters, and search tokens are limited to `\w+`.
- **Local channels:** the single-instance socket is private to the user.
- **Network:** the update check sends only a User-Agent; the model download is pinned to a revision
  and a SHA-256; the MCP server has input limits and is read-only by default. Every network request
  PRIVACY.md lists matches the code, and there are no others: the update check, the AI provider,
  Hugging Face, and Anki and Zotero on 127.0.0.1 without a proxy.
- **Feature claims:** spot checks (Naive Bayes over LSA, TF-IDF, Levenshtein and Jaro-Winkler;
  k-means and hierarchical clustering) match the code.
